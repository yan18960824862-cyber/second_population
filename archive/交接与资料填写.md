# 娜娜：物体模型与档案模板

## 当前样本怎么查看

在项目根目录执行 `python nocache_server.py`，打开 `http://127.0.0.1:8020/index.html`。进入系统，点击“外卖骑手 TRK-0001”：

1. 保留原空调版 6.6 秒扫描进场、连续三维旋转、淡出。
2. 档案按原有顺序逐块出现，照片式示意图和三维模型明确分开。
3. 点击主图下方 `3D VIEW`，拖动或用左右方向键查看现有代码模型。可自动旋转、暂停、复位、滚轮缩放。
4. 三维窗口内按 Esc 回到档案；档案内按 Esc 或 `BACK TO SCENE` 返回监控。返回时恢复原先播放或暂停的状态。
5. 从任意卡片进入，上一项、下一项均以当前目标为起点。切换、回放、关闭时清理先前的动画。

三维模型是程序生成的示意模型。骑手与货车、巴士、大巴、轿车、SUV、路灯均已增加结构细节；扫描与三维查看共用几何。档案插画和三维模型的细节不完全相同，不能当作精确重建。

右下角局部图已接入动态：货车为机构循环示意，轿车/SUV/巴士/大巴为散热与转子循环，路灯为灯组电流，骑手保留原能源模块的缓慢流动。具体机构不代表识别到了真实车辆的动力类型。底图保持稳定，减少动态偏好下显示静态图。

## 晓丽的文字放在哪里

`archive/records.json` 是独立资料表，当前整理了现有 40 个目标的编号、名称、类别、模型类别和原始识别备注。它不复制原数据中的模拟环境数值。当前仓库没有收到晓丽的单独文稿。

按 `objectId` 找到目标，填写：

| 字段 | 用途 |
| --- | --- |
| `description` | 档案身份表下的简短介绍 |
| `descriptionSource` | 这段介绍来自哪份文稿、哪位组员、哪个版本或哪个公开来源 |
| `details` | 附加资料数组；每条需要 `label`（字段名）、`value`（内容）、`source`（依据） |

`description` 非空必须有来源；`details` 不允许缺来源。原始识别备注仍只是项目标注，不代表独立核实。

完整来源在 `SOURCE NOTES` 展示。页面用文本方式显示资料，文字中包含 `<`、`&` 或引号不会被当成网页代码执行。

名称和类别目前与 `tracks.json` 严格对应；不要只改一个文件的名称造成错配。`model` 是示意模型家族，不是车辆品牌型号。

## 后续五个监控场景怎么接

先拿到对应场景的视频、目标清单与稳定编号，再逐个接入；当前没有假造五个场景的内容或切换按钮。

1. 由场景负责人把目标接入主站的数据流程。不同场景的 `objectId` 必须唯一。
2. 复制 `record-template.json` 的结构，加入 `records.json` 的 `records` 数组。
3. 编号、中文名、英文名、类别必须与新目标对应，模型从以下现有家族选择。
4. 填入带来源的文字，缺失字段留空。空调 `SP-0004` 继续走独立的 `ac-archive` 模块。
5. 检查：卡片 → 对应模型 → 对应档案文字 → 三维查看 → 返回原场景。后续场景切换逻辑由主站数据流程负责，本模块不生成视频识别坐标。

| category | model 可选值 |
| --- | --- |
| person | delivery、ebike |
| vehicle | sedan、suv、truck、coach、bus |
| infrastructure | streetlight |
| appliance | outdoorunit |

资料文件损坏、编号重复、类别不匹配或无来源的文字，会被目录校验拒绝，并回退到原有目标标注，避免让整个监控页面白屏。控制台会给出具体原因。

## 数据与合并边界

没有核实的能耗、用水和碳排放继续显示待补充。填入一般文字不会自动把碳排放变成“已验证”，也不会自动分配高低排放表情。

目前完成的是现有场景的可复用样本。晓丽的最终文字、后续五个场景及其逐物体模型核对仍需实际素材。

本次没有改团队开场、可视化、监控视频或原有 `tracks.json`。合并需要保留主站在 `index.html`、`tracker.js` 的其他修改，不能整份覆盖。
